> 2026年10月〜11月に話題になった、AIを使う攻撃フレームワーク **ARTEX** と、それを悪用したとされる攻撃キャンペーン（Storm-0940 / ConnectWise サプライチェーン侵害）について、**守る側（AppSec / クラウド / 情シス）の視点**で整理します。攻撃ツールは一切動かしません。事実は Microsoft の公式ブログ（一次情報）を基に、報道などの二次情報は [unverified] として区別します。

## 1. 導入：なぜ「AIが攻撃を自動化する」話が重要か

「AIで攻撃が自動化された」というニュースは、煽りと誤解が混ざりがちです。本記事の立場は最初に明言します。

> **ARTEX は“新種の脆弱性”ではありません。既知の手口（ID 悪用・OAuth アプリの信頼・サプライチェーン・パスワードスプレー）を、AI が「速く・大規模に」自動化したものです。**

だから守り方も**魔法ではなく、既知のID/クラウド衛生と予防（シフトレフト）が効く**——ただし「速度と規模」が上がった分、**検知と予防のスピード**がこれまで以上に問われる、というのが結論です。

## 2. 何が起きたか（一次情報：Microsoft 公式ブログ）

Microsoft Security Research / Threat Intelligence のブログ（2026-10-21）より [verified]。

### ARTEX とは

- Microsoft の表現：**「任意の AI モデルを使って多様な攻撃ワークフローを自動化できる、オープンソースの侵入テストフレームワーク」** [verified]。
- Go 製のマルチエージェント LLM システム（フロントは Next.js）。UI/出力は英語既定で、**日本語・中国語・韓国語・スペイン語に切替可**。
- LLM 駆動のエージェントが**偵察からデータ持ち出しまでを、ほぼ人手なしで自動実行**する。発見した資産・脆弱性をグラフに蓄積していく。
- **特定の AI モデル名は挙げられていません**（“any AI model”）。ツール本体と、そこに繋ぐモデルは別物です。

### 攻撃者 Storm-0940

- **中国国家と連携（China-state aligned）と評価**される攻撃者。2021年から活動、データ窃取が目的。
- Microsoft は **「最近開示された ConnectWise のサプライチェーン侵害（マルチテナントアプリ）の実行者が Storm-0940 だと評価」** [verified]。※これは断定ではなく **assessment（評価）** である点に注意。

### キャンペーンの規模とスピード

- ARTEX の使用は **2026年9月ごろから**、**世界で数百組織**が標的。航空宇宙・防衛、自動車、化学、エネルギー、金融、政府、法律、製造、メディア、半導体、ソフトウェア、シンクタンク等、幅広い。
- **「初期標的から特権アクセスまで 3 時間未満」** [verified]（複数事例）。
- ConnectWise 経路：ConnectWise Cloud Backup への不正アクセス → ARTEX で**2,250 を超えるテナント**に盗んだアプリ資格情報でサインイン → **アプリが既に持つ信頼を悪用して対話的ログインなしで認証** → 一部で Microsoft Graph / ディレクトリ操作（偵察、永続化のためのアプリ資格情報追加、ID・グループ・特権ロールの変更）。
- パスワードスプレー（10/10〜10/14）：8組織327アカウントに**15万超の失敗ログオン**、ピーク約2,900回/分。ただし**この スプレーでは認証成功・トークン発行・Graph 呼び出し・ディレクトリ変更は観測されず**。

### 正直に押さえるべき注記（誇張しないために）

- Microsoft 自身が **「標的の多くは成功していない」** と明記。一方で**短時間に多数の組織で特権的なクラウド永続化を達成**した、とも。
- **「アプリが存在する／認証が成功した」こと自体は、データアクセスや持ち出しを必ずしも意味しない**（Microsoft の注意書き）。
- **Microsoft 製品・社内システムの脆弱性が原因ではない**と明記。
- 国内の「日本企業にも痕跡」「約80社が標的の可能性」「15秒で個人情報収集」等は**報道・デモ由来の二次情報** [unverified]。「15秒」はセキュリティ企業 S&J が**自前テストサイト**に対して行ったデモ（架空データ）であって、実企業のデータ窃取ではありません。

## 3. 本質：新しい脆弱性ではなく「既知 TTP の AI 自動化」

Microsoft が挙げる MITRE ATT&CK は、**どれも“前からある”手口**です [verified]。

| フェーズ | テクニック |
|---|---|
| 偵察 | T1595 Active Scanning |
| 初期アクセス | T1078.004 Valid Accounts: Cloud／T1195 Supply Chain Compromise／T1199 Trusted Relationship |
| 権限昇格 | T1098.003 Additional Cloud Roles（アプリによる Global Admin 自己割当を含む）／T1098.001 Additional Cloud Credentials |
| 資格情報アクセス | T1528 Steal Application Access Token／T1555.006 Cloud Secrets Management Stores（Key Vault の一括読み出し） |
| 探索 | T1087.004 Cloud Account／T1580 Cloud Infrastructure Discovery |

つまり**攻撃の“種類”は新しくない**。AI が変えたのは：

- **速度**：標的から特権まで3時間未満。
- **規模／並列度**：2,250+ テナント、図では**4つのアプリ資格情報で4分未満に200+サインイン**。
- **人手の少なさ**：偵察〜持ち出しを自律実行。

**＝「攻撃者の単価と時間が劇的に下がった」**。これが防御にとっての本当の意味です。

## 4. だから効く防御（守る側の具体策）

### 4.1 Microsoft が挙げる緩和（ID／クラウド中心）[verified]

このブログの対策は **MFA やパッチの話ではなく、ID・OAuthアプリ・証拠保全**に寄っています。要点：

- 影響する ConnectWise アプリ接続は**正式な復旧手順が出るまで無効化**。
- **最初の対応でエンタープライズアプリを削除しない**（設定・証拠を先に保全）。
- 影響した**4つのアプリ ID を“表示名でなくアプリ ID で”棚卸し**し、各テナントのサービスプリンシパルの Object ID を記録。
- アプリが入っている／認可された**全 M365 テナントを、未使用でも確認**。
- Entra のサインイン／監査ログ、Purview Audit、SIEM、Graph テレメトリを**保全**（封じ込めを遅らせない）。
- **成功と失敗のサービスプリンシパル・サインインを分けてレビュー**。公開 IP だけに限定しない。
- 監査ログで、**アプリ/SP 資格情報の追加、新規アプリ・SP・所有者、ロール付与・同意、特権ロール割当、ユーザー・グループ・認証方法・条件付きアクセスの変更**を確認。確認できた不審は権限剥奪・資格情報ローテーション。
- **マルチテナントアプリの権限・同意に最小権限**。資格情報追加・特権付与・**高権限アプリの異常なアプリ単独（app-only）活動**を監視。

### 4.2 ここから導ける一般原則（ブログ外・業界の定石として明示）

> 注：以下は Microsoft ブログに“そのまま”は書かれていません。TTP から導ける一般的ハードニングとして、私の整理です。

- **アイデンティティが新しい境界**：OAuth アプリ／サービスプリンシパルの信頼は、そのまま攻撃面。**同意ガバナンス**（誰が何にアプリ同意できるか）、不要アプリの棚卸し、高権限アプリの定期レビュー。
- **MFA／条件付きアクセス／フィッシング耐性認証**：パスワードスプレーの前提を崩す（本件スプレーは失敗だったが、一般には必須）。
- **サプライチェーン＝自分の攻撃面**：ConnectWise のような第三者マルチテナントアプリは、入れた瞬間にテナントの一部。ベンダーのインシデント時に**自テナントのアプリ権限を即座に棚卸しできる状態**にしておく。
- **検知の速度**：3時間で特権を取られる前提なら、**“後で週次で見る”では遅い**。異常なアプリ単独活動・Key Vault の一括 SecretGet・特権ロール自己割当は**準リアルタイム検知**に寄せる。

### 4.3 検知：IOC とハンティング（ブログに具体がある）

Microsoft は IOC と Advanced Hunting / Sentinel クエリを公開しています [verified]。カテゴリだけ挙げます（詳細は原文を参照）：

- **IOC**：複数の攻撃元 IP、ユーザーエージェント（`Python-urllib`, `python-requests`, `curl`, `azure-toolkit` 等）、影響した3つの ConnectWise アプリ ID。
- **Defender/Sentinel のアラート**：「アプリが Global Admin を自己割当」「侵害された ConnectWise アプリに紐づく異常な Graph 活動」「既知の脅威アクター IP からのサインイン」等。
- **ハンティングの着眼**：OAuth アプリの存在・権限、SP のサインインとその後の Graph 活動、**Key Vault の SecretGet(200) を15分窓で集計し “1 ID が3つ以上の Vault に20回以上” を検出**、など。

> **「結果が空でも“アクセスがなかった証明”にはならない」**（Microsoft の注意）——ここも正直に。

## 5. AppSec／シフトレフト視点：なぜ“予防”の価値が上がるのか

ここが本記事の主張です。**AI が攻撃の単価と時間を下げるほど、「そもそも入られない・漏れていない」状態を“作る側の工程で”担保する予防（シフトレフト）の価値が上がります。** 事後検知だけでは3時間に間に合わない。

具体的に、今回のキャンペーンと直結する予防ポイント：

### 5.1 露出シークレット狩りへの対抗（ここは私の本丸）

Microsoft の関連ポスト（2026-11-05）では、**ARTEX が GitHub 上の OAuth アプリのシークレットを探すのに使われた**とされています [verified]。攻撃者が AI で**露出した鍵を大規模に収集**するなら、守りは：

- **シークレットスキャンの徹底**：GitHub Secret Scanning / Push Protection、`gitleaks`、`trufflehog` を CI と pre-commit に。
- ソースにハードコードされた鍵を**出荷前に止める**。拙作の OSS ルール集 [toi-cyber/semgrep-llm-security](https://github.com/toi-cyber/semgrep-llm-security) の `mcp-hardcoded-secret` も、`sk-…`/`ghp_…`/`AIza…` といった**シークレット形状のリテラルを静的に検出**します（＝ARTEX が狙う“露出鍵”の一部を、出荷前に潰す側の道具）。
- 前提として**最小権限・短命トークン・ローテーション**。漏れても被害を小さくする。

### 5.2 供給網・CI の衛生

- 第三者アプリ／アクション／依存の**権限と信頼を最小化**（SCA、Dependabot、アクションのピン留め）。
- CI に未信頼入力を持ち込む経路の遮断（別記事で扱った GitHub Actions の `pull_request_target` × 未信頼補間など）。AI 自動化は、こうした**取りこぼしを大規模に拾いに来る**。

### 5.3 まとめると
攻撃の自動化は「人海戦術が要らなくなった」こと。ならば守りも、**人の目に頼る事後対応から、仕組みで前倒しに潰す（静的解析・シークレットスキャン・最小権限・同意ガバナンス・準リアルタイム検知）**へ比重を移すのが合理的です。

## 6. 個人・中小組織向けの現実的な一手

大企業の Entra 運用まではできなくても、効果の高い基本はあります（IPA「中小企業の情報セキュリティ対策ガイドライン」も参照）：

- 公開資産（忘れられた古いサイト含む）の棚卸しと不要分の停止。
- 重要アップデートの適用、不要アカウント・権限の削除、**管理画面に MFA**。
- ログのレビュー体制と、怪しい挙動の連絡経路。侵入が疑わしいとき**自分でログ削除・設定変更をしない**。
- バックアップは**復元できるか試す**＋分離保管。
- 個人：漏えい通知は**メールのリンクでなく公式アプリ/サイトで確認**、パスワード使い回しをやめる、可能な所で MFA、漏えい報道に便乗する偽「今すぐ確認」メールに注意。

## 7. まとめ

- **ARTEX = 既知 TTP（ID 悪用・OAuth アプリ信頼・サプライチェーン・パスワードスプレー）の AI 自動化**。新しい脆弱性ではない。
- AI が変えたのは**速度・規模・省人化**。「3時間で特権」「2,250+ テナント」「4分で200+サインイン」。ただし **多くは失敗・標的≠侵害・Microsoft 製品の欠陥ではない**。
- 効く守りは**既知の ID/クラウド衛生＋予防（シフトレフト）＋検知速度**。Microsoft の緩和は ID・OAuth アプリ・証拠保全に寄っている。
- **予防の価値が上がる**：露出シークレット狩りにはシークレットスキャン（＋拙作ルールの `mcp-hardcoded-secret`）、供給網・CI 衛生、最小権限。
- 煽りに乗らず、**一次情報（Microsoft ブログ）で手口を分解し、既知の守りを“速く・仕組みで”回す**のが、AI 時代の等身大の答え。
